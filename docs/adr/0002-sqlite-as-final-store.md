# 以 SQLite 作为 Go 后端的最终数据源

迁移期间暂时由 Java 管理现有 JSON 数据，Go 通过存储抽象接入；迁移完成后，配置、订阅、任务状态和缓存由 SQLite 统一保存，JSON 仅用于导入导出，ZIP 用于备份。这样可以摆脱多个业务 JSON 文件之间的并发写入和一致性问题，同时允许不承诺旧版本数据格式的长期兼容。

## Considered Options

- 继续使用多个 JSON 文件：迁移成本最低，但并发写入、查询和任务状态恢复较弱。
- 引入独立数据库服务：能力更强，但增加部署和维护负担，不适合当前单机/Docker 应用定位。
- 使用 SQLite：单文件、无需额外服务，足以覆盖当前数据规模。

## Consequences

需要定义导入、导出和备份格式，并在迁移阶段实现 JSON 到 SQLite 的一次性导入；业务层不能再直接依赖 JSON 文件结构。

## 运行时访问说明

订阅与配置在运行时被服务层缓存在内存中（写穿缓存，而非每次读库）。**直接修改 `ani-rss.sqlite` 不会即时生效**：对运行中的进程来说 SQLite 是持久化层，不是读取时的真相来源。要修改订阅或配置，应走 `/api/setAni`、`/api/setConfig` 等正规接口，或重启进程让其从 SQLite 重新加载。
